# Reviewer-perspective audit before the full run (2026-11-01)

Inputs: the draft (`paper/main.tex`), the plan (`docs/JOURNAL_PLAN.md`), the
localstack pilot (all four techniques), and two counts made for this audit.

The question for each issue: **does fixing it later require re-running a
technique?** Evaluation-level choices (ground-truth filter, Poly-fix split,
universe R/T, parseable view, outcome metric, statistics) are computed from the
stored score files and cost minutes. Anything about *which bugs are scored*,
*how models are trained* or *how many runs exist* costs GPU-days. Only the
second kind must be settled now.

---

## A. Run-affecting — decide before the full run

### A1. The main claim rests on few bugs (statistical power)

The pilot showed that on localstack the BM25-vs-FLIM inversion comes entirely
from test assets; the claim a reviewer will accept is about
**behaviour-bearing** Poly-fix fixes. Their number in the test sets:

| | Mono | Poly behaviour-bearing | Poly test-asset-only |
|---|---|---|---|
| fold 1 | 483 | **71** (airflow 33, dolphinscheduler 23, others 15) | 142 |
| fold 2 | 505 | **71** (dolphinscheduler 31, airflow 21, others 19) | 135 |

With fold 1 only, the central comparison has 71 bugs, 79 % from two projects.
**Recommendation:** run **both folds** for every technique (142 bugs), and
spend compute on folds before seeds: one seed per fold for all projects, plus
seeds 42 / 2027 on fold 1 for three projects to measure seed spread (stated
as such). BM25 needs no training and can additionally score **every** bug
(3 594 + strata) at negligible cost, giving a descriptive BM25 picture on all
434 behaviour-bearing bugs.

### A2. The keep filter removed the purest case of the phenomenon

The keep filter (fix must touch a primary-language file) dropped 1 401 of
4 995 bugs. 417 have no counted file (docs/changelog only). The other **984
are fixes that change no Java/Python file at all**: 520 single-language fixes
in another language (mostly TypeScript/Vue front-end code in dolphinscheduler
and airflow, YAML/XML configuration), 374 fixes in non-programming files only
(configuration, schemas), and 90 multi-language fixes without the primary
language. For these, FLIM-strict and LocAgent can reach **no** ground-truth
file by construction, while BM25 and BLAZE can.

A reviewer will say: "the paper on multi-language fixes excluded the fixes
that contain no main-language code — the clearest case of the architectural
limit." The filter is defensible for the Mono-vs-Poly comparison (both
classes need a parseable target), but the stratum must not disappear.
**Recommendation:** add these bugs as a third scored stratum ("no
primary-language file"), exactly like the BeetleBox-removed bugs: scored in
the test windows by the models trained on the kept bugs (no retraining),
analysed separately, never pooled. Cost: scoring only (~20 % more scoring).
This is the only item in this list that changes the code's bug set, so it has
to be in before the full run.

### A3. "Architectural vs semantic" needs one ablation to be a claim, not an assertion

The brief's argument: a technique that ranks a file poorly can be improved
by training; one that cannot read it cannot. Our faithful BLAZE trains only on
source-language chunks (as the original), so its weak ranking of YAML/JSON
files is zero-shot. A reviewer can ask: "would BLAZE rank them if trained on
them?" Without the answer, the semantic half of the distinction is untested.
**Recommendation (optional but strong):** one ablation, *BLAZE trained on all
fix files*, fold 1, seed 13, the LR already selected — about 12–15 GPU-hours.
If its secondary-file ranks improve, the paper shows the semantic limit is
trainable while the architectural one is not.

### A4. LocAgent run-to-run variance (G16)

LocAgent samples at temperature 1.0. One run per bug is the published
protocol, but a reviewer will ask about variance. **Recommendation:** two
extra runs on a random 100-bug subset of fold 1 (~8 GPU-hours).

### A5. Tests in the training ground truth (keep as is)

Models are trained with test files as positives (as BeetleBox's ground truth
has them); sensitivity S1 removes tests at evaluation only. Retraining without
tests would double the runs. **Recommendation:** keep, and state it.

## B. Analysis / writing — fix after the runs, no rerun

| # | Issue | Fix |
|---|---|---|
| B1 | With 56 % of Poly-fix bugs test-asset-only, a headline on "all Poly-fix" invites the SANER objection. | Pre-register in the paper now: every RQ3/RQ4 result is reported for all Poly-fix, behaviour-bearing and test-asset-only, and with/without tests (S1); conclusions about the architectural limit are drawn from the behaviour-bearing rows. |
| B2 | Mono-vs-Poly differences are confounded by the number of GT files and by the share of test files. | `n_gt_reach` is a covariate; add the share of test GT files as a covariate. |
| B3 | FLIM-fallback beats FLIM-strict on Poly-fix (0.416 vs 0.361): a reviewer may read the limit as trivially fixable. | Show per-file-type ranks: the gain comes from reaching secondary files at low ranks (top-10 rate 11 % vs 48 % for BM25). |
| B4 | RQ2 can read as tautological ("a Java parser cannot parse YAML"). | Frame as quantification: 37 % of Poly-fix fix files and 100 % of the no-primary stratum (A2) are unreachable for the parser-dependent techniques. |
| B5 | Many outcomes × conditions × projects. | Designate one primary analysis (MAP, behaviour-bearing vs Mono, BM25 vs FLIM-strict, pooled model); everything else exploratory; Holm within families. |
| B6 | BLAZE at 2e-7 peaked at epoch 14 of 15. | Report; the paper's budget is kept; larger LRs converged and scored lower on validation. |
| B7 | Abstract says all four techniques "rank every file"; LocAgent returns ≤ 10 files. | Fix wording. |
| B8 | The behaviour-bearing signal is concentrated in airflow and dolphinscheduler. | Report per project; do not generalise beyond. |

## C. Checked and sound

Chronological split with purging; history features only from earlier fixes;
one universe and one ground truth for all techniques; expected ranks for ties;
LR selection on validation only; BLAZE trained from a public checkpoint and
never pooled; removed bugs analysed separately; LocAgent contamination probe
low (2.2 % hit@10 closed-book); random baseline far below every technique.
